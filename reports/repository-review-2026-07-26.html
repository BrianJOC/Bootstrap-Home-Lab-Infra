Reconstructed intention

Make a private homelab manageable by one person

The objective is a small, integrated platform on one Ubuntu management server, operated from an administrator’s laptop and later expanded to one or two physical nodes. It should provide familiar private hostnames, browser-trusted HTTPS, centralized identity and secrets, reproducible service deployment, and recoverable state. The tool resolves the initial dependency problem until GitLab can run the management workflows itself.

Easy to use at home

Internal DNS, trusted TLS, and Authentik should make private services feel ordinary to household users. Group membership should control access without separate account administration everywhere.

Safe to change alone

Reviewed code, saved plans, single resource ownership, pinned SSH identity, and explicit destructive boundaries make changes understandable and repeatable for one administrator.

Recoverable during failure

The home should retain core services before manual Vault unseal. NAS backups, offline copies, exact GitLab recovery, and a replacement-laptop kit should remove hidden dependencies on a surviving machine.

My interpretation of “done”: a complete operator journey: install → merge a useful service → enforce access → maintain it → survive reboot → recover from data or controller loss. A green stage list or remotely stored Terraform state is an intermediate milestone.

F2 · Follow-upA valid backup manifest does not establish a complete recovery set

Expected: required native artifacts for every enabled component, correct storage identity, and recoverable non-Vault components while Vault is sealed.

Observed: the backup script creates a k3s etcd snapshot but never copies that snapshot into its Restic staging tree. It copies /etc/technitium, while the actual DNS data bind mount is /opt/technitium/data or the configured data disk path. It copies /opt/authentik without following the configured alternate media path. No Kuma/Beszel configuration copy appears. Several copy failures are swallowed with || true; the manifest hashes whatever happened to be staged.

Example: all 30 hashes from the previous isolated restore can verify while Technitium zones and k3s recovery snapshots were never included. Hash verification proves integrity of included files, not coverage of the required artifact inventory.

When a Vault backup-token file exists but Vault is sealed, vault token renew or snapshot creation fails under set -e, before restic backup and the final status update. An earlier complete status can remain. The primary setup writes the “immutable” repository identity on each convergence; it does not compare and preserve an existing pin. Mount checks do not compare the expected NAS source, and the USB script neither validates a filesystem UUID nor unmounts after copying.

Completion test: put a unique canary in every required component, back up both default and secondary-disk layouts, destroy disposable state, restore it, and recover the canaries. Inject sealed Vault with an existing token, missing mounts, swapped repositories, and disconnected USB. Require explicit per-component results and a coverage manifest that fails on missing required artifacts.

Source trail: Required backup set and NAS/USB contract · Backup staging and status · Repository identity handling · USB copy · Actual DNS data mount · Authentik data paths

F3 · Follow-upThe critical checkpoint and unfreeze gate are weaker than the accepted recovery contract

Working foundation: named incidents, persistent GitLab freeze, exact installed-version comparison, native restore, shared-database isolation, application checks, and explicit unfreeze. The August record describes a destructive canary restore and eight recovered states; that remains useful historical evidence.

Observed gap: bootstrap-gitlab-checkpoint simply executes the ordinary full backup. There is no separate commit-bound Git bundle/state export in tmpfs, reopen verification, or newer-checkpoint reconciliation. A busy backup lock exits successfully without creating a new snapshot. The current generated pipeline correctly holds one platform-reconcile resource-group lease through apply, host reconciliation, health checks, and checkpoint, so another pipeline apply cannot interleave there. The checkpoint itself still does not receive or record CI_COMMIT_SHA.

The restore verifier prints the current critical commit and recovered state metadata but only checks that states exist and have a lineage/serial. It does not compare the expected set, commit, lineage, or serial from a recovery manifest before writing the verified marker. Read-only drift plans, OIDC login, and a Runner canary are absent from that gate.

Completion test: two queued applies with an overlapping nightly backup must produce distinct verified checkpoints tied to each applied commit and state set. Restore an older full backup plus the newer checkpoint. Inject a missing workspace, wrong lineage, and unrelated Git commit; each must keep automation frozen. Treat this as source work as well as a missing drill.

F4 · Follow-upController recovery currently opens a bundle; it does not recover a controller

Working foundation: checksummed archive, protected writes, independently encrypted SSH key using Argon2id/AES-GCM, password rejection, and isolated restore staging. The archive itself is gzip; the SSH key has its own encryption, and Restic supplies repository encryption.

Observed: the bundle contains serialized config, known hosts, the optional encrypted SSH key, and a small manifest. It lacks the accepted controller/target identity markers, source/release verification reference, ownership/backend checkpoint metadata, recovery instructions, and path relocation. Configuration retains the original laptop’s absolute paths. recover-controller ends after extraction with an instruction to inspect before adoption; no controller-adoption command, target audit flow, or compromised-controller rotation is implemented there.

Concrete consequence: successfully decrypting the SSH key on a temporary directory does not prove that a blank laptop can reconstruct the handoff guards and manage the existing target without replaying bootstrap. Server adoption into MAAS is a different operation and does not fill this gap.

Completion test: a blank disposable controller with a different username and no old home directory must use only the documented recovery kit to verify identity, reconstruct configuration/state references, audit without mutation, and explicitly adopt. Test preserved-credential recovery and a synthetic compromised-controller rotation separately.

Source trail: Accepted bundle, audit, adoption, and rotation contract · Bundle contents and Restore · Bundle refresh and target copy · recover-controller command · Current bundle tests

F5 · Follow-upApplication upgrades have a dispatcher, not the promised maintenance system

Working foundation: security-only unattended Ubuntu updates, disabled automatic reboot, a timer, protected proposal/hook directories, deadline fields, incident/backup checks, and a host-side executor.

Observed: no Renovate configuration or proposal producer is present, and no component upgrade hooks are installed. The dispatcher reads hand-authored proposal deadlines but does not consume the effective policy JSON to derive them. It does not enforce the configured admission-window end, rejected versions, backup freshness, major/stateful classification, vendor upgrade stops, compatibility, migrations, health, or rollback. It trusts a proposal’s requires_backup flag and then runs a root-owned hook if one exists.

Consequence: the default application_upgrades_enabled: true can enable a timer that has no actual upgrades to process. This is incomplete accepted behavior, not a reason to reopen the chosen review/deadline policy.

Completion test: one stateless fixture and one stateful fixture traverse proposal → review/deadline → scheduled execution → health/rollback. Prove rejection, stale backup, expired window, unsupported version path, and prior failure all block mutation; prove GitLab’s own executor survives GitLab downtime.

Source trail: Accepted upgrade policy · Installed maintenance files · Dispatcher gates · Effective policy output

F6 · Product gapMonitoring is a useful minimum, but key visibility and paging behavior are missing

Working foundation: bounded Kuma/Beszel containers, local agent, health JSON, consecutive-failure counters, direct provider payloads, journald retention, and a documented inability to page through total host loss. Observed gaps: the health adapter does not consume backup age/completeness, USB age, upgrade blockers, reboot age, or certificate-sync state. Kuma’s retention input is passed from Go but not applied by the role. Completion test: synthetic sealed Vault, stale backup, overdue upgrade, and failed notification delivery must produce distinct correct states. F7 · Product gapThe wizard and lifecycle convergence do not implement the full configuration promise

Observed: the wizard collects host/domain/network basics and bootstrap secrets, but has no backup-enable choice, destination, schedule/retention editor, paging choice, or test alert. New config starts with backups and paging disabled. Round-tripping pre-existing YAML values is useful, but does not implement the accepted first-run backup profile (PRD 16).

LifecycleStage.Check checks a version marker, helper existence, and selected enabled/running units. It does not compare a desired configuration digest. Changing retention or the maintenance schedule while keeping the same enabled features can therefore be treated as complete and skipped. Disabling upgrades/monitoring also lacks an inverse check that ensures the old enabled runtime is removed or stopped.

Completion test: complete a new wizard with the recommended backup profile and with an explicit trial choice. F8 · Product gapCertificate renewal still depends on a manual synchronization step

Working foundation: host timer, file-based Cloudflare credential, renewal staging, hostname/key/expiry checks, atomic active-version switch, and rollback trap.

Observed: every successful renewal touches certificate-vault-sync-pending; it never tries to update an available Vault. The implemented synchronization is in the operator’s bootstrap vault reconcile command. Thus normal renewal can leave the authoritative Vault certificate stale even when Vault was unsealed throughout.

Some reload errors are ignored; the Vault curl check does not reject HTTP failure statuses. The script does not verify the served certificate identity for every TLS consumer or validate the full candidate chain as required by the decision. Those source gaps remain even if initial issuance was proven with Pebble.

Completion test: renew with Vault healthy and sealed; healthy Vault must receive the same new fingerprint automatically, and sealed Vault must defer safely and synchronize on recovery. Inject each consumer’s reload/identity failure and prove rollback to the previous served certificate.
